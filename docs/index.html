This is all you write to get /api/v1/books 
# 1. Register the kind in the data layer
ENTITY_KINDS=book

# 2. Declare the schema + expose the route
APP_KINDALIASPATHS_0_ALIAS=books
APP_KINDALIASPATHS_0_NAME=book
APP_KINDALIASPATHS_0_SCHEMA={"required":["author"]}

# That's it. You now have:
#   GET    /api/v1/books          (paginated, filterable)
#   POST   /api/v1/books          (validated, auth-gated)
#   GET    /api/v1/books/:id
#   PATCH  /api/v1/books/:id      (field-masked per role)
#   DELETE /api/v1/books/:id      (distributed-locked)
#   GET    /api/v1/books/count
#
#   + live OpenAPI spec (personalized per caller)
#   + AI agents can read & act on the spec directly

The real cost of a "simple" backend

Every SaaS backend hides the same iceberg

The endpoint is five minutes. The infrastructure around it takes weeks — and grows for years. These are the problems Tarcinapp has already solved.

01

Auth is never just auth

JWT validation, multi-issuer support, role extraction, field-level permissions, and visibility scoping that can't be bypassed by a crafted query — all needs testing, maintenance, and security auditing.

02

Multi-tenancy is a data model problem

Ownership, visibility, viewer access, and group membership need to be baked into every record from day one. Retrofitting it onto an existing schema is painful. Tarcinapp's managed fields handle this automatically.

03

Distributed systems bite quietly

Concurrent writes to the same record produce silent data corruption without distributed locking. Rate limiting prevents abuse. Idempotency keys stop duplicate records on retries. None of this is trivial.

04

Content lifecycle is always custom-built

Pending → active → expired states, approval workflows, scheduled publishing, soft deletion with audit trail — every SaaS product ends up building this. Tarcinapp ships it as primitives on every record type.

05

AI agents need a trustworthy API surface

An AI coding agent is only as good as the API spec it reads. Tarcinapp generates a live, personalized OpenAPI spec per caller — shaped by real roles and policies. No stale docs, no spec drift. The agent sees exactly what the user is allowed to do.

06

Your logic goes in one place

The Orchestration Layer gives you a clean Pre/PostProcessor hook for every endpoint. Enrich data, enforce quotas, emit events — without touching the infrastructure. Domain logic and infrastructure never mix.

What you get immediately

Infrastructure you don't have to build

Everything in this list is live — not planned, not a roadmap item. It works today, from a schema definition — for your team, your users, and your AI agents.

🔐

Fine-Grained Authorization

OPA-powered policies enforce who can do what at the field level — not just the route level. Role-based field masking means different users see different response shapes on the same endpoint, automatically.

🗂️

Polymorphic Data Model

Five generic record types model any business domain without migrations. The same deployment handles books, products, orders, and playlists — all differentiated by a single _kind field.

⚙️

Configuration Over Code

A new resource type is a handful of environment variables. JSON Schema validation, uniqueness rules, rate limits, and named field sets are all configuration — zero code to write or maintain.

🏢

Multi-Tenancy Built In

Visibility rules, ownership fields, and role hierarchies are part of the data model. Every record carries _ownerUsers, _ownerGroups, _viewerUsers, and _visibility — all enforced at query level.

⏱️

Lifecycle Management

Every record has a built-in state machine: pending → active → expired. Content moderation, scheduled publishing, and soft deletion with a full audit trail — all from two timestamp fields.

🤖

AI & Human-Ready API Surface

The gateway generates a live, personalized OpenAPI spec per authenticated caller. AI coding agents, human developers, and the self-rendering admin UI all read the same spec — always accurate, role-scoped, and drift-free.

Data Model

Five types model any domain

Every business entity maps to one of five generic record types, differentiated by the _kind field.

Entity /entities

Primary domain objects. Anything that is a "thing" in your domain.

bookproductarticleauthor
List /lists

Groupings and collections of entities. Containers that organize your domain objects.

bookshelfplaylistwishlist
Relation /relations

Many-to-many join between a list and an entity, with arbitrary metadata on the link.

book-in-shelfitem-in-cart
Entity Reaction /entity-reactions

User interactions on entities. Supports threaded hierarchies for replies.

reviewratingbookmark
List Reaction /list-reactions

User interactions directed at a specific list.

shelf-likeplaylist-comment

Lifecycle

Every record has a state machine

Records move through three states driven by two timestamp fields — no custom code required. Use it for content moderation, scheduled publishing, and soft deletion with a full audit trail.

  • Pending — awaiting approval, visible only to the owner and admin roles
  • Active — live, publicly accessible per visibility settings
  • Expired — soft-deleted, retained for audit, accessible only by admins
