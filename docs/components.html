entity-persistence-service

LayerV — Data
TechnologyNode.js · LoopBack 4 · MongoDB
Default Port3000
StatusImplemented ✓
GitHubtarcinapp/entity-persistence-service

What It Does

EPS is the data layer — the only component that talks directly to MongoDB. It is intentionally simple: it stores and retrieves JSON records with no domain intelligence, no authorization logic, and no business rules. All of that lives above it in the Gateway layer.

EPS exposes 67 REST endpoints across 9 controllers, covering all five record types plus hierarchy traversal and through-access routes.

entity-persistence-gateway

LayerIII — Gateway & Security
TechnologyJava 21 · Spring Cloud Gateway · Spring Boot 3 · Redis
Default Port8081
StatusImplemented ✓
GitHubtarcinapp/entity-persistence-gateway

What It Does

The gateway is the system's single entry point and its Policy Enforcement Point. No request reaches EPS without passing through all gateway checks. It has two broad responsibilities: security enforcement and domain transformation.

Security Features

  • JWT Authentication — validates RS256/HS256 tokens; supports multiple issuers (e.g., Keycloak + another IdP). Fails fast with 401 on expired or unsigned tokens.
  • OPA Authorization — two-pass check on every request. Pass 1: operation allow/deny + visibility set injection. Pass 2: field-level allow/deny lists.
  • Field Masking — removes forbidden fields from request bodies (before forwarding) and response bodies (before returning). The masking is structural: absent keys, not null values.
  • Distributed Locking — Redis-backed lock per record ID for all write operations. Prevents lost updates in concurrent scenarios.
  • Rate Limiting — per-kind sliding-window rate limiter backed by Redis. Configurable replenish rate and burst capacity per alias.
  • Request Size Limiting — default 1 KB hard limit on request bodies. Configurable per kind alias.

Domain Transformation Features

  • Kind Alias Routes — maps domain paths (/books, /shelves) to generic EPS paths with automatic _kind injection.
  • JSON Schema Validation — per-kind schema validated against incoming request bodies before forwarding.
  • Dynamic OAS Generation — generates a personalized OpenAPI spec per caller, shaped by their roles and OPA policies. Cached in Redis.
  • Query Abstraction — adds simplified query parameters (limit, skip, s, q, fieldset) as aliases for LoopBack's verbose filter syntax.
  • Saved Queries — named query templates resolvable via ?q=name.
  • Field Sets — named field projection presets resolvable via ?fieldset=name.
  • Response Caching — configurable Redis-backed local cache for GET responses. Automatically invalidated on writes.

Route Topology

The gateway manages approximately 140 routes: the base set of generic routes (EPS proxy) plus kind-alias routes (one per configured alias, including hierarchy and traversal sub-routes). Each route passes through a configured chain of filters.

entity-persistence-gateway-policies

LayerIII — Authorization
TechnologyOPA (Open Policy Agent) · Rego
Default Port8181 (OPA default)
StatusImplemented ✓
GitHubtarcinapp/entity-persistence-gateway-policies

What It Does

This repository contains the Rego policies loaded into OPA. The gateway calls OPA on every authenticated request. The policies define the authorization rules that the gateway enforces.

Policy Structure

  • Operation policies — allow/deny decisions for each HTTP method + resource combination. A member can POST to /books. Only an editor can PUT (full replace). Only an admin can bulk-PATCH.
  • Field policies — per-field allowedFields (for read) and writableFields (for write) per role. A member cannot write _validFromDateTime. A viewer cannot see _ownerUsers.
  • Visibility injection — policies inject sets filters into every list query. A member query automatically gets sets[actives]=true&sets[owners][userIds]=<sub> — they can never see others' pending records even if they try to craft a filter to access them.

Role Naming Convention

# Application-level roles (operation control)
tarcinapp.records.entity.admin
tarcinapp.records.entity.editor
tarcinapp.records.entity.member

# Field-level roles (field access control)
tarcinapp.fields.entities._validFromDateTime.create
tarcinapp.fields.entities._ownerUsers.update

entity-persistence-universal-orchestrator

LayerIV — Orchestration
TechnologyJava 17 · Quarkus · Apache Camel
Default Port8082
StatusPartial ◑
GitHubtarcinapp/entity-persistence-universal-orchestrator

What It Does

The orchestrator is an optional middleware that gives you a clean, well-structured integration point for custom business logic. It exposes Apache Camel routes for each EPS endpoint, with a PreProcessor that runs before forwarding to EPS and a PostProcessor that runs after receiving the response.

The orchestrator is designed to be cloned and extended — you fork it per product, implement your processors, and wire the gateway to point to your orchestrator instead of directly to EPS.

Pipeline Pattern

Gateway → Orchestrator
             → RouteBuilder (dispatches to correct route)
               → PreProcessor (your logic: enrichment, validation, rejection)
               → EntityPersistenceClient (calls back to Gateway → EPS)
               → PostProcessor (your logic: side effects, enrichment)
           → Gateway (field masking, response)

Available Patterns

  • Auto-Enrich — fetch from an external service in PreProcessor and inject fields into the request body
  • Quota Enforcement — count existing records and short-circuit with 422 if the limit is exceeded
  • Async Notification — in PostProcessor, publish an event to RabbitMQ/Kafka after a successful write
  • Response Aggregation — make multiple EPS calls and merge the results in PostProcessor
  • Cascade Soft-Delete — on entity delete, also soft-delete all related reactions

EntityPersistenceClient

Important: The EntityPersistenceClient always calls back through the Gateway — not directly to EPS. This ensures all authorization and field masking is applied even on internal calls. Always forward the original Bearer token when using it.

tarcinapp-base-gui

LayerI — Client
TechnologyReact 18 · Vite · Tailwind CSS · React Router v6
Default Port5173 (dev) / varies in production
StatusPartial ◑
GitHubtarcinapp/tarcinapp-base-gui

What It Does

A domain-agnostic admin and explorer UI. On first load, it fetches the live OpenAPI spec from the connected Gateway and builds the entire interface from it: navigation, data grids, create forms, edit modals, and traversal pages. No hardcoded domain knowledge. The same unmodified codebase serves as the UI for a books app, a product catalog, a CRM, or any other domain.

OAS-Driven Rendering

  • Sidebar navigation — one entry per OAS tag that owns a root collection endpoint. Sorted by x-base-record-type (entity → list → relation → reaction).
  • Data grids — columns derived from actual response data. System fields shown first, then custom fields alphabetically.
  • Create forms — fields from the POST request body schema. Boolean → toggle, enum → select, datetime → datetime-local, array → chip input.
  • Edit modals — inline PATCH editing. Multiple fields can be staged before a single PATCH submission.
  • Traversal pages — sub-resource pages (e.g., /books/{id}/chapters) from OAS path patterns.

Two Connection Modes

  • Live mode — connect to a running Gateway URL with a Bearer token. The JWT is validated client-side before connecting (expiry, structure). Username and roles from the token are displayed as a preview.
  • Offline / drag-and-drop — drop a local .json OAS file onto the setup screen. The full interface is built from the local spec. Useful for previewing domain projections before deploying.
