Architecture

How Tarcinapp's six layers work together to deliver a full SaaS backend — from the browser to MongoDB.

Core Philosophy

Tarcinapp is built around one central insight: the vast majority of SaaS backends solve the same structural problems — multi-tenancy, access control, lifecycle management, and domain-specific CRUD APIs. The application-level difference between a bookstore API and a product catalog API is mostly naming and schema constraints, not architecture.

The suite separates two concerns that are almost always conflated:

  • Structural concerns — authentication, authorization, data model, query language, lifecycle: Tarcinapp handles these as infrastructure.
  • Domain concerns — which fields does a "book" have? What happens when an order is placed? What validation is specific to your business? These belong in configuration and the Orchestration Layer.

The result: a new domain entity is a handful of environment variables. A new authorization rule is a Rego policy. Custom business logic has exactly one well-defined home.

Layer I: Client

Implemented: tarcinapp-base-gui — React 18 · Vite · Tailwind CSS. A domain-agnostic admin UI that builds its entire interface from the Gateway's live OpenAPI spec. No hardcoded domain knowledge. Connecting to a different Gateway URL produces a completely different UI for a completely different business domain.

Planned: tarcinapp-ui-server — a Server-Side Rendering engine for public-facing SaaS frontends.

Layer II: Identity Management

Keycloak handles all authentication concerns: OAuth2/OIDC flows, JWT issuance, user management, and role assignment. It is deployed as a standard infrastructure component — no custom repository. The Gateway validates JWTs issued by Keycloak (and optionally multiple other issuers) on every request.

JWT claims carry user ID, roles, and email-verification status. The Gateway extracts these and passes them to OPA for every authorization decision.

Layer III: Gateway & Security

The most feature-rich layer. entity-persistence-gateway is the system's single entry point and its Policy Enforcement Point. Every request passes through it. Nothing reaches the data layer without passing all gateway checks.

Key responsibilities:

  • JWT Authentication — validates token signature, issuer, expiry; rejects unsigned or expired tokens with 401.
  • OPA Authorization — two-pass check: (1) may the caller perform this operation at all? (2) which fields are readable/writable?
  • Field Masking — strips fields from responses that the caller's role cannot see. Adds managed fields (_createdBy, _ownerUsers, etc.) from JWT claims.
  • Domain Projection — turns /entities into /books by rewriting paths, injecting _kind, and applying per-kind JSON Schema validation.
  • Dynamic OpenAPI Generation — generates a personalized API spec per caller. Fields the caller cannot access are absent from the spec. This drives the GUI.
  • Rate Limiting — per-kind sliding-window rate limiter backed by Redis.
  • Distributed Locking — acquires Redis locks per-record for all write operations to prevent lost updates.
  • Response Caching — configurable local cache backed by Redis.

Layer IV: Orchestration

entity-persistence-universal-orchestrator is an optional, thin middleware between the Gateway and the Data layer. It exposes Pre and PostProcessor hooks for every endpoint — giving you a clean integration point for custom business logic without modifying any core component.

Use the orchestrator for: data enrichment from external services, cross-record quota enforcement, async side effects (publishing events), and response aggregation. See the Orchestration Layer concept for the decision guide: Gateway filter vs. OPA policy vs. Orchestrator.

Layer V: Data, Search & Storage

entity-persistence-service is intentionally simple: it stores and retrieves JSON records from MongoDB. It has 67 REST endpoints covering all five record types, hierarchies, traversals, and lookups — but zero domain intelligence. All business constraints come from the Gateway layer.

Redis provides distributed locking (driven by the Gateway), rate limiting state, and local response caching. Meilisearch (planned: entity-search-gateway) will provide full-text search.

Layer VI: Event & Reaction Layer (Planned)

An event backbone based on Kafka/Redpanda and a suite of Camel Quarkus services for CDC event production, transformation, and consumption. This layer enables async workflows, audit streams, and real-time derived data — but has no existing repositories yet.

Request Flow

A typical authenticated read request travels through these stages:

  1. Client sends GET /api/v1/books?q=my&limit=10 with Bearer token.
  2. Gateway validates JWT signature and expiry → extracts sub, roles, groups.
  3. Gateway calls OPA: "May this user GET from /books?" → OPA returns allow/deny + injected query constraints (sets, filter[where]).
  4. Gateway rewrites path: /books → /entities?filter[where][_kind]=book. Appends OPA-injected visibility scoping.
  5. Gateway checks Redis cache. If cached, returns immediately.
  6. (If orchestrator configured) Orchestrator PreProcessor may modify the request further.
  7. EPS executes query against MongoDB. Returns raw results.
  8. (If orchestrator configured) Orchestrator PostProcessor may enrich or transform the response.
  9. Gateway field-masks the response: strips any fields OPA said the caller cannot read.
  10. Gateway caches the masked response in Redis (if caching enabled).
  11. Response returned to client with only the fields they are authorized to see.

Gateway Transforms: The Domain Projection Magic

Domain Projection is how the Gateway turns a generic /entities API into a domain-specific /books API with four transformation steps:

StepWhat it does
Path RewritingGET /books → GET /entities
_kind InjectionOn write: adds "_kind":"book" to request body. On read: adds filter[where][_kind]=book to query.
Schema ValidationApplies the per-kind JSON Schema to the request body before forwarding.
OAS PruningRemoves the generic /entities routes from the spec if domain-only mode is enabled.
