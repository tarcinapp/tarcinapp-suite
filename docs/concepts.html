Core Concepts

The foundational ideas that make Tarcinapp work — data model, security, domain projection, and the orchestration layer.

The Data Model

Tarcinapp uses a polymorphic data model: all business data maps onto five generic record types stored in MongoDB. A single deployment can store books, shelves, reviews, and user follows — all using the same five types, differentiated by the _kind field.

This design makes the system radically reusable: adding a new resource type never requires schema migrations, new collections, or new service code. It is purely a configuration change.

Five Record Types

TypeCollectionPurposeTypical _kind values
EntityentitiesPrimary domain objects — anything that is a "thing"book, product, author
ListlistsGroupings / collections of entitiesbookshelf, playlist, wishlist
Relationlist-entity-relationsMany-to-many join between a list and an entity, with metadata on the link itselfbook-in-shelf, item-in-cart
EntityReactionentity-reactionsUser interaction on a specific entity; supports threaded hierarchyreview, rating, bookmark
ListReactionlist-reactionsUser interaction on a specific listplaylist-like, shelf-comment

Managed Fields

Every record across all five types is automatically decorated with managed fields — underscore-prefixed system attributes injected, enforced, or computed by the gateway and EPS. Callers never need to supply these; they cannot be forged.

The _kind Discriminator

_kind is the field that differentiates records within the same MongoDB collection. It is:

  • Injected by the gateway for Kind Alias routes (calling POST /books automatically sets "_kind":"book")
  • Immutable after creation — changing it returns 422 IMMUTABLE-ENTITY-KIND
  • Used by the gateway to apply kind-specific JSON Schema validation, rate limits, and saved queries
  • Used by EPS to enforce allowed kinds and apply per-kind record limits

Hierarchies

Entities, Lists, EntityReactions, and ListReactions all support parent-child trees via the _parents field. Relations do not support hierarchy.

Setting _parents on a child record automatically updates the parent's _children array. When a child is deleted, EPS removes it from the parent's _children automatically.

POST /entities
{
  "_name": "Chapter 1",
  "_kind": "chapter",
  "_parents": ["tapp://localhost/entity/book-uuid-here"]
}

GET /entities/{bookId}/children      ← direct children
GET /entities/{chapterId}/parents    ← direct parents
GET /entities?filter[where][_parentsCount]=0  ← root items only

The tapp:// URI Scheme

The _parents field uses tapp:// URIs to reference parent records. The format is:

tapp://localhost/{recordType}/{uuid}

Examples:
  tapp://localhost/entity/a1b2c3d4-...
  tapp://localhost/list/e5f6g7h8-...
  tapp://localhost/entity-reaction/d9e0f1a2-...

Note: _listId and _entityId on Relation and Reaction records are plain UUIDs, not tapp:// URIs. Only _parents and arbitrary custom reference fields use the tapp:// scheme.

Any field (not just _parents) can hold a tapp:// URI. The filter[lookup] query parameter resolves these references at query time, embedding the referenced record inline. Lookup resolution is subject to the same authorization rules as direct access — the caller must have permission to see the referenced record.

Record Lifecycle

Every record has a lifecycle state derived from two timestamp fields. No explicit "status" field exists — state is always computed from the timestamps:

Visibility

Every record has a _visibility field with three levels:

ValueWho can access
publicAll authenticated users — but only when the record is active
protectedDirect owners, _ownerGroups members, _viewerUsers, _viewerGroups, and appropriate roles
privateOnly _ownerUsers, _viewerUsers, and admin/editor. Group ownership is disabled.

Common Gotcha: A record with _visibility: public that is still pending is NOT visible to the public. Visibility only takes effect when a record is active. A pending record is always restricted to its owner and admin roles.

Security Flow

Every request goes through a deterministic security pipeline before any data is touched:

  1. JWT validation — signature, issuer, expiry. Rejects with 401 if invalid.
  2. OPA Pass 1: Operation authorization — may this role perform this HTTP method on this resource? Returns allow/deny + sets injection (visibility scoping query constraints).
  3. OPA Pass 2: Field authorization — which fields may this role read/write? Returns allowed/forbidden field lists.
  4. Field masking on request — strips forbidden fields from request body before forwarding to EPS.
  5. Managed field injection — adds _createdBy, _ownerUsers, etc. from JWT claims.
  6. Field masking on response — strips forbidden fields from the EPS response before returning to caller.

Role Hierarchy

RoleCapabilities
adminFull access. Can see and modify all records regardless of ownership or visibility. Can set any managed field.
editorBroad read/write. Can approve content (set _validFromDateTime). Cannot modify other users' ownership fields.
memberStandard user. Can create, read own records, update own records. Cannot approve content or see others' private records.
(none / anonymous)Public read-only access to active + public records. No write access.

Role names follow the convention tarcinapp.records.entity.admin, tarcinapp.records.entity.member, etc. Field-level roles follow tarcinapp.fields.entities._validFromDateTime.create.

OPA Two-Pass Authorization

Every authorized request results in two OPA calls:

  • Pass 1 — Operation Check: Input is the HTTP method, path, and JWT claims. Output is allow: true/false plus setFilters — additional query constraints the gateway must inject (e.g., sets[actives]=true&sets[owners][userIds]=user-id). This ensures callers can never query records they shouldn't see, even if they craft clever filter queries.
  • Pass 2 — Field Check: Input is the allowed operation result. Output is lists of allowed/forbidden fields for both read and write. The gateway uses this to strip fields from both the request body (before forwarding) and the response body (before returning).

Field Masking

Field masking is structural — forbidden fields are physically absent from the JSON, not replaced with null or a placeholder. A caller who cannot see _ownerUsers receives a response body that literally does not contain that key. The GUI uses this: if a field is absent from the OAS spec, no column or form field is rendered for it — zero client-side access control logic needed.

Distributed Locking

For all write operations (POST, PUT, PATCH, DELETE on single records), the gateway acquires a Redis-backed distributed lock before forwarding to EPS. This prevents concurrent writes from producing lost updates or corrupted records. The lock key is derived from the record's ID. Locks are released after the operation completes, including on error. If a lock cannot be acquired within the configured timeout, the gateway returns 409 Conflict.

Domain Projection

Domain Projection is how the gateway turns the generic /entities API into a domain-specific /books API — without changing EPS at all. It is purely a gateway-layer transformation.

Kind Aliases

Kind Aliases are the configuration unit of Domain Projection. Each alias maps a URL path segment to a _kind value and optionally carries schema, rate limits, field sets, and saved queries:

# Expose /api/v1/books backed by entities with _kind=book
APP_KINDALIASPATHS_0_ALIAS=books
APP_KINDALIASPATHS_0_NAME=book
APP_KINDALIASPATHS_0_SCHEMA={"type":"object","required":["author"],"properties":{"author":{"type":"string"}}}

# Expose /api/v1/shelves backed by lists with _kind=shelf
APP_KINDALIASPATHS_1_ALIAS=shelves
APP_KINDALIASPATHS_1_NAME=shelf

# Expose /api/v1/reviews backed by entity-reactions with _kind=review
APP_KINDALIASPATHS_2_ALIAS=reviews
APP_KINDALIASPATHS_2_NAME=review

Dynamic OpenAPI Generation

The gateway generates a personalized OpenAPI spec per authenticated caller:

  • Fields the caller may not read are absent from GET response schemas → the GUI does not render them as columns
  • Fields the caller may not write are absent from POST/PATCH schemas → the GUI does not include them in forms
  • Routes the caller may not access are absent entirely → the GUI renders no Create/Edit/Delete button for those operations

The GUI implements zero client-side access control logic. It renders exactly what the spec describes. Changing a user's role or updating an OPA policy is immediately reflected in the UI on the next spec fetch.

Orchestration Layer

The universal-orchestrator is an optional, thin middleware that sits between the Gateway and EPS. It exposes PreProcessor and PostProcessor hooks for every endpoint, giving you a well-defined integration point for custom business logic.
