Books App — End-to-End

The canonical Tarcinapp example. A books application with multi-role access, hierarchical chapters, shelves, and reviews — all from configuration, no code.

Domain Design

The books app uses these record types:

ResourceRecord Type_kindNotes
BooksEntitybookPrimary domain object with author, isbn, genre fields
AuthorsEntityauthorSeparate entity; linked to books via publisherId / lookup
ChaptersEntitychapterChild entities of books via _parents
ShelvesListshelfContainers for books; users create personal shelves
Book-in-ShelfRelationbook-in-shelfThe join record when a book is added to a shelf
ReviewsEntityReactionreviewUser reactions on books; supports threaded replies
RatingsEntityReactionratingNumeric rating; uniqueness: one per user per book

Step 1: Configure EPS

# Allowed kinds
ENTITY_KINDS=book,author,chapter
LIST_KINDS=shelf
LIST_ENTITY_REL_KINDS=book-in-shelf
ENTITY_REACTION_KINDS=review,rating,bookmark

# Uniqueness: no duplicate books by same user (same slug)
ENTITY_UNIQUENESS="where[_kind]=${_kind}&where[_slug]=${_slug}&where[_createdBy]=${_createdBy}"

# One rating per user per book
ENTITY_REACTION_UNIQUENESS="where[_kind]=rating&where[_entityId]=${_entityId}&sets[owners][userIds]=${_createdBy}"

# Books need approval; shelves and reviews auto-approve
AUTOAPPROVE_ENTITY=false
AUTOAPPROVE_LIST=true
AUTOAPPROVE_ENTITY_REACTION=true

# Default visibility
VISIBILITY_ENTITY=protected
VISIBILITY_LIST=private

Step 2: Configure the Gateway

app:
  name: books-app
  shortcode: books
  kindAliasPaths:
    # Books (Entity) — with JSON schema
    - alias: books
      name: book
      schema: |
        {
          "$schema": "https://json-schema.org/draft/2020-12/schema",
          "type": "object",
          "required": ["author"],
          "properties": {
            "author":  {"type": "string", "minLength": 1},
            "isbn":    {"type": "string", "pattern": "^[0-9-]{10,17}$"},
            "genre":   {"type": "string"},
            "pages":   {"type": "integer", "minimum": 1}
          }
        }
      # Named queries
      queries:
        - name: my
          query: "sets[owners][userIds]=${sub}"
        - name: by-genre-scifi
          query: "filter[where][genre]=sci-fi"
      # Named field sets
      fieldSets:
        - name: summary
          fields: "_id,_name,_visibility,author,genre"
        - name: full
          fields: "*"
      # Hierarchy alias for chapters
      hierarchyAlias: chapters
      hierarchyName: chapter

    # Shelves (List)
    - alias: shelves
      name: shelf

    # Authors (Entity)
    - alias: authors
      name: author

    # Reviews (EntityReaction)
    - alias: reviews
      name: review

    # Ratings (EntityReaction)
    - alias: ratings
      name: rating

Step 3: API Calls Walkthrough

Create a book (as member)

curl -X POST http://localhost:8081/api/v1/books \
  -H "Authorization: Bearer $MEMBER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "_name": "The Great Gatsby",
    "author": "F. Scott Fitzgerald",
    "genre": "classic",
    "isbn": "978-0743273565"
  }'

# Response: 201 Created
# Note: _validFromDateTime is null → book is PENDING (needs admin approval)

Approve the book (as admin)

curl -X PATCH http://localhost:8081/api/v1/books/{bookId} \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"_validFromDateTime": "2024-01-01T00:00:00Z"}'

# Response: 200 OK — book is now ACTIVE and visible to others

Create a shelf and add a book

# Create a shelf
curl -X POST http://localhost:8081/api/v1/shelves \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"_name": "My Favorites", "_visibility": "private"}'

# Add a book to the shelf (creates a list-entity-relation behind the scenes)
curl -X POST "http://localhost:8081/api/v1/shelves/{shelfId}/entities/books" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"addedNote": "This changed my perspective"}'

# List books in the shelf
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8081/api/v1/shelves/{shelfId}/entities/books"

Create chapters (hierarchy)

curl -X POST "http://localhost:8081/api/v1/books/{bookId}/chapters" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "_name": "Chapter 1: The Valley of Ashes",
    "pageStart": 1,
    "pageEnd": 18
  }'

# List chapters of a book
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8081/api/v1/books/{bookId}/chapters"

Write a review

curl -X POST "http://localhost:8081/api/v1/books/{bookId}/reactions/reviews" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "_name": "A timeless masterpiece",
    "body": "Fitzgerald captures the hollow decadence of the Jazz Age perfectly.",
    "rating": 5
  }'

Adding a New Kind

This checklist applies every time you introduce a new resource type. Uses the books app as the starting point — adding a publisher entity.

No code required. A new _kind is always a configuration-only change. New code is only needed if the new kind requires custom business logic beyond what JSON Schema validation covers.

The Checklist

  1. Decide the record type: Entity, List, Relation, or Reaction
  2. Consider if you need hierarchy (only Entities support _parents)
  3. Consider if you need traversal access (e.g., /books/{id}/reactions/reviews)
  4. Add the _kind to EPS ENTITY_KINDS (or variant) → restart EPS
  5. Add a kind alias in the gateway (APP_KINDALIASPATHS_N_*) → restart gateway
  6. Optionally add JSON Schema, uniqueness rules, record limits, rate limiter
  7. Test the new endpoint
  8. Verify in the GUI (the new resource appears in the sidebar after reconnect)

Example: Adding publisher Entity

# EPS — add to ENTITY_KINDS (and restart EPS)
ENTITY_KINDS=book,author,chapter,publisher

# Optional: globally unique publisher names (across all users)
ENTITY_UNIQUENESS="where[_kind]=${_kind}&where[_slug]=${_slug}&where[_createdBy]=${_createdBy},where[_kind]=publisher&where[_slug]=${_slug}"
# Gateway — add kind alias (and restart gateway)
APP_KINDALIASPATHS_5_ALIAS=publishers
APP_KINDALIASPATHS_5_NAME=publisher
APP_KINDALIASPATHS_5_SCHEMA={"type":"object","required":["country"],"properties":{"country":{"type":"string","minLength":2},"founded":{"type":"integer","minimum":1400}}}
# Test
curl -X POST http://localhost:8081/api/v1/publishers \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"_name": "Penguin Books", "country": "UK", "founded": 1935}'

# Verify schema validation
curl -X POST http://localhost:8081/api/v1/publishers \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"_name": "Missing Country"}'
# Expected: 422 ValidationError — country is required

Custom Business Logic

When JSON Schema validation isn't enough — you need to call an external service, enforce a quota that spans multiple records, or emit an async event after a write — implement the logic in the Orchestration Layer.

Workflow

1

Fork the universal-orchestrator template

git clone https://github.com/tarcinapp/entity-persistence-universal-orchestrator.git my-product-orchestrator
cd my-product-orchestrator
2

Implement your PreProcessor

For every endpoint, there is a route class (e.g., CreateEntityRoute.java). Override the PreProcessor class for the route you want to customize:

// Example: ISBN enrichment via external API
@ApplicationScoped
public class CreateBookPreProcessor implements PreProcessor {

  @Override
  public void process(Exchange exchange) throws Exception {
    // Read the kind from the header injected by the Gateway
    String kind = exchange.getIn().getHeader("X-Tapp-Kind", String.class);
    if (!"book".equals(kind)) return;  // only run for book creates

    // Get the request body
    Map<String, Object> body = exchange.getIn().getBody(Map.class);
    String isbn = (String) body.get("isbn");

    if (isbn != null) {
      // Call external ISBN API and enrich
      BookInfo info = isbnService.lookup(isbn);
      body.put("pageCount", info.getPageCount());
      body.put("publishYear", info.getYear());
      exchange.getIn().setBody(body);
    }
  }
}
3

Wire the Gateway to use the orchestrator

app:
  backend:
    host: http://localhost:8082  # ← Point to orchestrator, not EPS directly

The orchestrator forwards to EPS internally. The Gateway only talks to the orchestrator.

4

Test end-to-end

curl -X POST http://localhost:8081/api/v1/books \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"_name": "Clean Code", "author": "Robert C. Martin", "isbn": "978-0132350884"}'

# Expected: pageCount and publishYear are in the response,
# injected by your PreProcessor from the ISBN API

Pattern: Hierarchy (chapters of a book)

# Gateway config: enable hierarchy alias on books
APP_KINDALIASPATHS_0_ALIAS=books
APP_KINDALIASPATHS_0_NAME=book
APP_KINDALIASPATHS_0_HIERARCHYALIAS=chapters
APP_KINDALIASPATHS_0_HIERARCHYNAME=chapter

# Routes created:
# GET  /api/v1/books/{id}/chapters    ← list children
# POST /api/v1/books/{id}/chapters    ← create child with _kind=chapter and _parents set automatically

Pattern: Relations (books in shelves)

# Add a book to a shelf — creates a list-entity-relation
curl -X POST "http://localhost:8081/api/v1/shelves/{shelfId}/entities/books" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"position": 1, "addedNote": "Top pick"}'

# Query books in a shelf with traversal
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8081/api/v1/shelves/{shelfId}/entities/books?limit=10"

# The response includes _fromMetadata (shelf info) and _toMetadata (book info)
# on each item, giving you denormalized join-record metadata.

Pattern: Reactions (reviews on books)

# Post a review on a book
curl -X POST "http://localhost:8081/api/v1/books/{bookId}/reactions/reviews" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"_name": "Loved it", "body": "...", "score": 5}'

# List all reviews for a book
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8081/api/v1/books/{bookId}/reactions/reviews"

# Reply to a review (threaded reaction via _parents)
curl -X POST "http://localhost:8081/api/v1/books/{bookId}/reactions/reviews" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "_name": "Reply",
    "_parents": ["tapp://localhost/entity-reaction/{reviewId}"]
  }'

Pattern: Toggle Reaction (bookmarks)

# EPS: one bookmark per user per book (uniqueness enforcement)
ENTITY_REACTION_KINDS=review,rating,bookmark
ENTITY_REACTION_UNIQUENESS="where[_kind]=bookmark&where[_entityId]=${_entityId}&sets[owners][userIds]=${_createdBy}"
# Toggle pattern:
# First POST → 201 Created → bookmark added
# Second POST → 409 Conflict (UNIQUENESS-VIOLATION) → already bookmarked
# To unbookmark: GET /bookmarks?filter[where][_entityId]={bookId}&q=my → get the ID → DELETE /bookmarks/{id}

curl -X POST "http://localhost:8081/api/v1/books/{bookId}/reactions/bookmarks" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"note": "Read for the book club"}'

Pattern: Approval Workflow

# EPS: books require approval (no auto-approve)
AUTOAPPROVE_ENTITY=false

# Member creates a book → it's PENDING
# Only the owner and admin/editor can see pending records

# Admin approves by setting _validFromDateTime
# (Requires tarcinapp.fields.entities._validFromDateTime.create role)
curl -X PATCH http://localhost:8081/api/v1/books/{bookId} \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -d '{"_validFromDateTime": "2024-01-01T00:00:00Z"}'

# To reject (soft-delete) a book without approving it:
curl -X PATCH http://localhost:8081/api/v1/books/{bookId} \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -d '{"_validUntilDateTime": "2020-01-01T00:00:00Z"}'
# The book moves to EXPIRED state → effectively rejected

# Query pending records (admin only)
curl -H "Authorization: Bearer $ADMIN_TOKEN" \
  "http://localhost:8081/api/v1/books?sets[pendings]=true"
